# Visual Evidence Register

This register tracks thesis figures that are not generated diagrams, especially screenshots, report captures, browser captures, source-document captures, and external visual materials. It complements `figure-register.md`.

Status values:

- `CANDIDATE`
- `NEEDS_CAPTURE`
- `NEEDS_SOURCE`
- `NEEDS_LICENSE_REVIEW`
- `NEEDS_EVIDENCE`
- `READY_FOR_REVIEW`
- `INSERTED_IN_CHAPTER`
- `DEFERRED`
- `REJECTED`

Rules:

1. Prefer self-captured project screenshots over internet images.
2. Do not include screenshots that expose credentials, access tokens, private account data, private project workflow details, or unnecessary personal information.
3. External internet images, benchmark charts, model diagrams, or thesis-sample captures must be used only when they add clear academic value and have a registered source, citation, and copyright/license review.
4. Do not screenshot another thesis table or benchmark as evidence unless the source is cited and reuse is legally and academically appropriate. Prefer paraphrasing, recreating a small original comparison table, or citing the source directly.
5. Screenshots of execution results, HTML reports, traces, `results.xml`, terminal output, or GitHub project evidence must come from a known run or verified project state.
6. All accepted visual evidence must be copied under `docs/thesis-workspace/assets/figures/` and registered here before insertion into a chapter or appendix.
7. Candidate screenshots do not receive final thesis figure numbers until the target chapter draft is being prepared or revised.

|---|---|---|
| Chapter 1 | Low. A screenshot is not required for the introduction unless a concise SUT context image is explicitly approved later. | Usually use no figure. Do not insert an external software testing pyramid or test automation pyramid image; Chapter 2 already covers the foundations and F-01 is excluded from thesis insertion. Defer any source-safe SUT screenshot to Chapter 3. |
| Chapter 2 | Low. This chapter is now a Literature Review focused on theoretical background and methodology. | Use concise prose and citation-backed tables by default. Do not insert repository-specific technical diagrams or external screenshots unless the outline is explicitly re-approved and source/license review is complete. |
| Chapter 3 | Moderate. Sanitized Unsplash SUT and API documentation screenshots help non-specialist readers understand what is being tested and which public API documentation informs the scenario scope. | V-01 and V-12 are inserted as contextual visual evidence. |
| Chapter 4 | Moderate. Scenario screenshots can support implementation examples, while tooling screenshots can help readers see the implemented API/UI test organization. | V-13 is inserted as implementation-context evidence. Keep V-02/V-03 optional unless they add more value than prose and tables. |
| Chapter 5 | High. Verified report, trace, execution output, result artifacts, and carefully adapted external benchmark charts can support evaluation evidence. | V-04, V-05, V-10, and V-11 are inserted in the main chapter with clear evidence boundaries; V-06 remains represented through tables/file artifacts. |
| Chapter 6 | Low. Conclusion should normally not introduce new screenshots. | Reuse prior evidence only if necessary. |
| Appendices | High. Appendices can hold detailed report, trace, command, and artifact screenshots without crowding the main chapters. | Use Appendix D for verified execution artifacts and Appendix E for optional workflow artifacts. |
